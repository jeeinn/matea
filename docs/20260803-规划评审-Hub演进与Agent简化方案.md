## 二、P0 级问题（必须在冻结 Phase 1 前解决）

### P0-1 · 任务 1.1.4「按 role 决定 task_type」会导致可复现的功能回归

**文档主张**（TASKS 1.1.4）：
> 合并 Assign 与 @mention 触发语义，统一视为「拉 Agent 进入会话」；根据 `role` 决定 task_type。

**代码事实**：当前是**两套不相交的 task_type 词表**。

`internal/workflow/resolver.go:189` — Assign 路径：
```go
func (r *Resolver) taskTypeForRole(role string, evt *webhook.WebhookEvent) string {
	switch role {
	case store.RoleAnalyze: return "analyze_issue"
	case store.RoleCoder:   /* label=bug */ return "fix_bug" / "solve_issue"
	case store.RoleReview:  return "review_pr"
	}
}
```

`internal/workflow/resolver.go:347` — mention 路径：
```go
func (r *Resolver) commentTaskType(agent *store.Agent, forceDev, forceReply bool, ...) string {
	if forceDev   { return "solve_comment" }
	if forceReply { return "reply_comment" }
	switch agent.Role {
	case store.RoleAnalyze: return "reply_comment"   // read-only
	case store.RoleCoder:   return "solve_comment"
	case store.RoleReview:  return "reply_comment"   // read-only
	}
}
```

**具体回归案例**：`@matea-review` 出现在 Issue 评论中
- 现状：`commentTaskType` → `reply_comment` → InteractionRunner → 正常回话 ✅
- 按 role 单因子合并后：→ `review_pr` → L1 门禁 `checkReviewRequiresPR`（`internal/workflow/gate_l1.go:35`）判定无 PR → **拒绝执行，用户视角是"@了 Agent 但它不理我"** ❌

**第二个回归**：`@matea`（analyze）在评论区
- 现状：`reply_comment`，走 `analyze-readonly` 工具包（`runners.go:299`），轻量回话
- 合并后：`analyze_issue`，触发完整分析流程 —— token 成本、耗时、评论噪音全部放大，且会推进 workflow stage

**根因**：task_type 不是 `role` 的函数，而是 **`(role × surface × intent)` 的函数**。
- `surface`：issue / pull_request
- `intent`：承接工单（assign / review_requested）vs 会话续写（mention / 斜杠命令）

这两个维度携带的信息量无法由 role 恢复。文档把"触发语义统一"（正确）和"task_type 推导简化"（错误）混为一谈了。

**建议改法**：保留"拉 Agent 进入会话"作为统一的 **Intent 语义层**（这部分是对的，用户心智确实应该统一），但 task_type 由一张**显式解析表**决定，而不是 switch：

```go
// internal/workflow/tasktype_table.go
type resolveKey struct {
	Role    string // analyze | coder | review
	Surface string // issue | pr
	Intent  string // assign | mention | slash_dev | slash_reply | review_requested
}

var taskTypeTable = map[resolveKey]string{
	{RoleAnalyze, "issue", "assign"}:           "analyze_issue",
	{RoleAnalyze, "issue", "mention"}:          "reply_comment",
	{RoleCoder,   "issue", "assign"}:           "solve_issue",   // label=bug 时覆写为 fix_bug
	{RoleCoder,   "issue", "mention"}:          "solve_comment",
	{RoleReview,  "pr",    "review_requested"}: "review_pr",
	{RoleReview,  "pr",    "mention"}:          "reply_comment",
	{RoleReview,  "issue", "mention"}:          "reply_comment",  // 关键：不能推成 review_pr
	// ...
}
```

收益是双份的：既避免回归，又让 Phase 3「策略配置化」有天然落点——这张表往 YAML 一搬就是可配置策略，比拆 switch 容易得多。

**任务清单改写建议**：把 1.1.4 拆成三条独立可验收项：
- 1.1.4a 抽取 `(role, surface, intent)` 三元组解析表，**行为完全等价于现状**（纯重构，单测锁定现有全部映射）
- 1.1.4b 统一 Intent 命名与用户可见文案为「拉 Agent 进入会话」（只改文案与日志，不改路由）
- 1.1.4c 补齐 Assign 分支缺失的 `ResolveLogicIssueAndPR` 与 `Force`（见 P1-4）

### P0-2 · 任务 1.1.3「Agent 名自动映射 Gitea username」存在账号劫持风险

**代码事实** — `internal/agents/manager.go:105-133`：
```go
user, err := m.gitea.GetUser(username)
if user != nil && m.gitea.ValidateUserToken(username, currentToken) {
	return currentToken, false, nil
}
password := generatePassword()
if user == nil {
	// AdminCreateUser(...)
} else {
	// ⚠️ 用户已存在但 token 校验失败 → 直接重置密码
	if err := m.gitea.AdminUpdateUserPassword(username, password); err != nil { ... }
}
```

当前风险可控，因为 `gitea_username` 必须由用户**手工输入**（`web/src/views/Agents.vue:393-421` 的向导只填 `name`，不填 `gitea_username`），属于显式行为。

**一旦 1.1.3 做成"Agent 名自动映射 username"**，在一个已存在真人账号 `matea`（或 `matea-coder`）的 Gitea 实例上创建 Agent，会走到 `else` 分支：**静默重置该真人账号的密码，并以其身份签发 API Token**。这等同于账号接管，且无任何确认提示。

**必须补的防护**（建议直接写进 1.1.3 验收条件）：
1. **托管标记**：在 `agents` 表或 Gitea 用户描述里标记"由 Matea 创建"，`AdminUpdateUserPassword` 分支**仅对已标记账号**生效
2. **冲突即报错**：自动映射命中已存在且非 Matea 托管的账号时，**创建失败并提示改名**，绝不静默接管
3. **接管需显式确认**：确需接管既有账号时，走单独的 UI 确认流程，明确告知"将重置该账号密码"
4. `gitea.auto_provision: false`（1.5.3 已规划）时，自动映射只做名称建议，不触碰 Gitea

这条即使不做 1.1.3 也建议单独修——现有 `else` 分支本身就偏危险，只是触发概率低。

## 四、P2 级问题（架构接口设计）

### P2-1 · `HubBackend.Execute` 同步阻塞语义与项目既有的可靠性能力矛盾

```go
Execute(ctx context.Context, task *TaskContext) (*BackendResult, error)
```

Matea 现有的可靠性资产：SQLite 持久化任务队列 + webhook 收件箱 + `ReplayAccepted` 崩溃重放。而 `solve_issue` 交给 Hub 做多轮 tool-use，实际耗时可能是**数分钟到数十分钟**。一次同步 HTTP 调用意味着：

- Matea 进程在此期间重启 → 任务状态彻底丢失，Hub 侧可能还在跑（产生孤儿会话与重复副作用）
- 无进度反馈，用户在 Gitea 上只看到长时间无响应
- 无法表达"已提交给 Hub，等待回调"这个中间态

**建议在 Phase 1 就把异步形态定死**（Phase 2 再改接口，所有实现都要返工）：

```go
type HubBackend interface {
	Name() string
	// 提交任务，返回可持久化的句柄；实现可选择同步完成（Done=true）
	Submit(ctx context.Context, task *TaskContext) (*Handle, error)
	// 按句柄轮询/等待结果，支持 Matea 重启后凭 DB 中的 handle 恢复
	Poll(ctx context.Context, h *Handle) (*BackendResult, State, error)
	Cancel(ctx context.Context, h *Handle) error
	Capabilities() HubFeatures
	HealthCheck(ctx context.Context) error
}

type Handle struct {
	Backend       string
	RemoteID      string // Hub 侧 session/job id
	IdempotencyKey string // 防重复提交
}
```

注意 `CodingResult.RemoteSessionID`（`internal/agents/coding_backend.go:82`）已经在为 OpenCode 存远端会话 ID —— 说明这个需求在现有代码里已经冒头了，接口设计应当吸收它。

### P2-2 · `HubCapabilities` 六个静态 bool 容易变成谎言，且命名与决策 #1 撞车

- **粒度问题**：同一个 Hub 完全可能对 analyze 支持 tool-use、对 code 不支持；`SupportsToolUse bool` 表达不了。建议改为按 task_type 的能力矩阵，或定义为"声明 + 运行期降级"两段式。
- **命名冲突**：决策 #1 是「**仅 role，不做多 capabilities**」，同一份文档里又定义 `HubCapabilities`。虽然是不同层，但 TASKS 1.1.1 还要在 Agent UI 上显示 "capabilities 别名"，三者叠加极易误读。建议 Hub 侧改名 `HubFeatures` 或 `BackendProfile`。

### P2-3 · builtin「fallback」是空头承诺

决策 #9 写「保留为默认与 **fallback**」，但全文没有任何降级机制设计：Hub 超时 / 502 / 鉴权失败时怎么办？`HealthCheck()` 定义了却没说**谁调用、多久调一次、失败后的策略**。

两条路选一条：
- 补设计：熔断阈值 + 自动降级到 builtin + 在 Gitea 评论中显式告知"本次由内置后端处理，可能与 Hub 记忆不连续"
- 或改措辞：删掉 "fallback"，明确 Hub 故障即任务失败并重试，避免承诺未实现的行为

### P2-4 · `strings.HasPrefix(agent.Backend, "hub-")` 分流过于脆弱

字符串前缀匹配的失败模式是**静默的**：拼错成 `hub_opencode`、`Hub-hermes` 都会悄悄回落 builtin，用户以为在用 Hermes，实际在烧自己的 LLM 额度。

建议改为显式注册表查找：
```go
backend, ok := registry.Lookup(agent.Backend)
if !ok {
	return fmt.Errorf("unknown backend %q for agent %s", agent.Backend, agent.Name)
}
```
未知 backend **必须报错**，不得回落。这也解耦了 P1-2 的命名问题——注册表键名可以自由定，不依赖 `hub-` 前缀约定。

### P2-5 · `TaskContext.Tools` 的调用传输契约缺失

结构体里内联了 `Tools []ToolDef` 和 `SandboxPath`，但**远端 Hub 如何回调这些工具**没有定义。§6.3 说 2b 阶段走 "Matea MCP tools"，可这意味着 `TaskContext` 里真正该传的是 **MCP endpoint + 会话级 token + 工具白名单**，而不是内联的 `ToolDef` 列表。

Phase 1 的类型定义若不把这层说清，Phase 2b 一定会推翻 `TaskContext`。建议现在就明确：
```go
// 仅 code 任务
SandboxPath string
ToolAccess  *ToolAccessGrant // MCP endpoint + 短期 token + 允许的工具集 + TTL
```

### P2-6 · `ExternallyHandled` 与 `HandlesGit` 语义重叠，且削弱核心原则

两个 bool 表达的是同一件事的两面（谁拥有写回权），却分散在 `BackendResult` 和 `HubCapabilities` 两处。建议合并为单一枚举，并在门禁层显式校验：

```go
type WriteOwnership string // "matea" | "hub"
```

否则「Matea 永远握 Gitea 写回权与 workflow 门禁」这条原则（§5.2）在实现层没有强制点，容易被逐渐侵蚀。

### P2-7（补充）· MCP Server 只有认证没有授权

§7.2 的 `matea_create_issue` + `matea_assign_agent` 组合，等价于**远程触发沙箱代码执行**。当前设计只有 `api_key | mtls` 的**认证**，没有**授权**——一把 key 等于全部仓库、全部 Agent、全部工具的完整权限。

建议在 2.3.2 补：per-key 的 repo allowlist + 允许调用的工具子集 + 速率限制 + 审计落库（项目已有 `operation_logs` 表，直接复用）。

同理 §7.3 的 deliver webhook：出站事件**无签名、无重试、无 DLQ、无顺序保证**。Matea 对入站 Gitea webhook 是验签的（`internal/webhook/signature.go`），出站理应对称地做 HMAC 签名，否则接收端无法验证来源真伪。

## 六、Agent 配置简化方案专项讨论

### 6.1 四条子任务的现状与实施要点

| 子任务 | 代码现状 | 真实工作量 | 关键要点 |
|---|---|---|---|
| 1.1.1 role 兼容 / capabilities 别名 | **已完全满足**；capabilities 从不存在 | **0**（应删除或改为文档任务） | 不要引入 capabilities 别名，那是净负债 |
| 1.1.2 UI 默认模板 | `applyRoleWizard` 已实现 name + 双 prompt 预设 | **小**（改造现有向导） | 补 backend 预设 + gitea_username；命名迁移需全局同步 |
| 1.1.3 名字自动映射 username | **不存在**；两字段独立，创建后禁用编辑 | **中**（含安全加固） | 见 P0-2，必须先做托管标记与冲突保护 |
| 1.1.4 触发语义合并 | 两套独立词表 | **大**（含回归风险） | 见 P0-1，必须保留 surface 维度 |

### 6.2 关于 role 字段与 capabilities 别名映射

结论已在 P1-1 说明：**不要做这个别名映射**。

理由：
1. `capabilities` 在代码里从不存在，引入别名等于凭空造概念
2. 一个概念两个名字，是文档、UI、API、日志四处不一致的源头
3. 用户真正需要的不是"别名"，而是**理解 role 意味着什么**——这靠 UI 文案解决，不靠字段名

**替代建议**：在 Agent 编辑页的 role 选择器下方直接展示该 role 的**行为契约**（可从 6.4 的解析表自动生成，不是硬编码文案）：

> **分析（analyze）**
> · 被 Assign 到 Issue → 产出完整需求分析评论
> · 在评论中被 @ → 简短回话（只读，不改代码）
> · 可用工具：read_file / list_files / search_code（只读）

这比任何字段别名都更能降低认知成本，且随解析表自动同步、不会过期。

### 6.3 关于三 Agent 默认模板

**做法上的三点补充**：

1. **模板 ≠ 硬限制，文档必须写明**。TASKS 1.1.1 标题「固定 role，默认三 Agent 模板」有歧义：是"role 是闭集"还是"只能有三个 Agent"？
   `Agent.Repos []string` 字段的存在说明系统本就支持按仓库特化。若被误读为硬限三个，`matea-coder-go` / `matea-coder-fe` 这类多语言/多仓库场景就没法做，`Repos` 字段直接变成死代码。
   **建议措辞**：「role 为闭集 `analyze|coder|review`；同一 role 可存在多个 Agent 实例（按仓库/技术栈特化）；UI 默认提供三个开箱模板。」

2. **`@matea` 这个命名有可供性陷阱**。`matea` 是产品名，用户看到 `@matea` 的第一直觉是"这是总入口"，于是会 @它说"帮我把这个 bug 改了"——而 role=analyze 会安静地产出一篇分析，用户体感是"它没听懂"。

   三个选项：
   - **A（推荐，最省事）**：改名 `matea-analyst`，三个名字对称（`matea-analyst` / `matea-coder` / `matea-review`），杜绝"总入口"误解
   - **B（体验最好，成本高）**：`@matea` 真的做成**分诊 Agent**，按评论意图路由到 coder / review，或至少在识别到编码意图时回一句「这类需求请 @matea-coder，或回复 /dev 由我转交」
   - **C（折中）**：保留 `matea` 为分析 Agent，但在 role=analyze 的 prompt 里加一条：识别到用户在要求改代码时，明确提示应 @matea-coder

   当前文档方案是"名字像总入口、行为是专职分析"，是三者中认知失配最严重的一种。

3. **模板应预设 backend 且默认 `builtin`**，与"5 分钟可用"的定位一致；Hub backend 只在进阶章节引导（1.6.2 已规划，一致）。

### 6.4 关于 Assign 与 @mention 语义合并的实现方式

**用户心智层统一是对的，路由层不能塌缩。** 建议的分层：

```
Gitea 事件
  ↓
Intent 解析（统一层）—— 语义都是「拉 Agent 进入会话」
  · who     : 哪个 Agent（registry.GetByGiteaUsername，两条路径已一致）
  · surface : issue | pr
  · intent  : assign | review_requested | mention | slash_dev | slash_reply
  · scope   : logicIssueID / prID（Assign 分支需补齐，见 P1-4）
  · force   : bool（Assign 分支需补齐）
  ↓
task_type 解析表（role × surface × intent → task_type）
  ↓
Runner / 工具包 / 门禁（全部维持现状，无需改动）
```

这样做的好处：
- **门禁层零改动**。三层门禁全部按 `role` 判定（`gate_l1.go:33`、`dispatcher/gates.go:35`、`context.go:31`），对"Assign vs mention"本来就无感知，合并不冲击它们。
- **Runner 层零改动**。`RunnerFactory.GetRunner`（`runners.go:309`）按 task_type 分发，只要 task_type 集合不变就不用动。
- **改动集中在 resolver 一个文件**，可用表驱动测试完整锁定。

**必须一并处理的两个既有问题**：

1. **斜杠命令的裸匹配 bug**。`resolver.go:301-319` 用 `strings.Contains(body, "/dev")` 判定——评论正文里出现 `/development`、`http://x/dev`、或代码块中含 `/dev` 都会误触发。合并时应顺手改为：行首锚定 + 剥离代码块（``` 与行内 `code`）+ 完整词边界。
2. **`/dev` 与 `/reply` 的定位**。它们是 mention 词表**唯一的覆写入口**，在解析表模型里应作为独立的 `intent` 值（`slash_dev` / `slash_reply`）而非布尔 flag，语义更清晰，也便于 Phase 3 扩展更多命令。

另注意 `/matea reset` 在更上游的 `internal/dispatcher/pipeline.go:21-45` 短路处理，**早于 `Resolve()`**。合并 Intent 时应决定：是把它也收进 Intent 模型（更统一），还是明确保留为"元命令"旁路（更简单）。文档需给出立场，否则实现者会各写各的。

## 七、对用户体验的影响评估

### 7.1 净收益

- **心智模型对齐现实**：「Agent = 有职位的同事」，@谁就知道会发生什么。相比"配置一个 Agent 然后勾选它会什么"，这是明显更好的产品直觉。
- **消除高频配错项**：role 是单选闭集，用户没有配错的自由度。
- **onboarding 缩短**：三个模板一键创建，配合自动映射 username，从"建 Agent"到"能 @"的步骤显著减少。

### 7.2 需要警惕的体验退化

| 风险 | 触发场景 | 缓解 |
|---|---|---|
| **静默不响应**（最严重） | P0-1 的回归：@matea-review 在 Issue 里被门禁挡掉 | 保留 surface 维度；另外**任何门禁拒绝都应在 Gitea 回一条简短说明**，绝不静默 |
| **误 @ 后行为不符预期** | 用户 @matea 要求改代码，得到一篇分析 | 见 6.3 第 2 点的命名/分诊方案 |
| **回话成本放大** | analyze 的 mention 从轻量 reply 变成完整分析 | 保留 `reply_comment` 与 `analyze-readonly` 工具包的区分 |
| **命名迁移造成文档与现网不一致** | 存量用户 Agent 叫 `code-analyzer`，文档全写 `@matea` | 提供改名引导；文档同时标注"若你的 Agent 沿用旧名，请替换为你的实际 Agent 名" |
| **自动映射造成账号意外** | P0-2 | 冲突即报错 + 显式确认 |

### 7.3 一条通用建议

「简化」的成败取决于**失败路径是否可见**。当前设计里，Agent 不响应的原因（不在 registry / 门禁拒绝 / 未知 backend / Hub 不可达）**全部是日志级的**，用户在 Gitea 上只看到"没反应"。

建议把「静默失败」列为本轮简化的显式验收项：**任何被识别为"意图触发 Agent"但最终未执行的事件，都应在 Gitea 上留下一条简短说明**（含原因与建议动作）。这对体验的提升，很可能大于三个模板本身。

## 八、对扩展性与可维护性的评估

### 8.1 role 闭集的扩展成本

`role` 目前作为闭集散落在 **5+ 处 switch**：
`internal/workflow/resolver.go:189` / `:347`、`internal/dispatcher/gates.go:39,50,57`、`internal/workflow/context.go:35-39`、`internal/workflow/gate_l1.go:35`、`internal/workflow/session.go:49`。

若未来要加第 4 个 role（`triage` / `test` / `doc` 都是很自然的需求），需要改 5 个以上文件，且**漏改一处是静默的**（`default` 分支会兜底成 analyze，行为错误但不报错）。

**建议趁这次简化收敛成一张描述表**：

```go
type RoleSpec struct {
	Name         string
	TaskTypes    map[SurfaceIntent]string // 复用 6.4 的解析表
	ToolPack     string
	Gates        []GateID
	StageOnStart string
	StageOnDone  string
}
var roleSpecs = map[string]RoleSpec{ /* analyze, coder, review */ }
```

这既服务于「简化」这个当前目标（一处定义、UI 文案可自动生成），又让加 role 从"改 5 处代码"变成"加一条数据"，同时是 Phase 3「策略配置化」（3.3 / 3.4）最自然的落点。**用一次重构同时还掉三笔债**，性价比很高。

### 8.2 简化方案本身不损害灵活性 —— 前提是三条边界写清楚

1. role 是闭集，但 **Agent 实例数不限**（同 role 可多实例，按 repo 特化）
2. task_type 由 `(role, surface, intent)` 决定，**三个维度都不可省略**
3. backend 与 role **正交**（每个 Agent 独立配 backend，这点文档已明确，很好）

只要这三条成立，简化的是**配置界面**，不是**能力空间**——这正是好的简化。反之，若把三条中任何一条误读成"系统只支持三个 Agent"或"task_type 只看 role"，简化就变成了能力阉割。

### 8.3 架构演进的灵活性判断

| 演进方向 | 当前设计是否支撑 | 备注 |
|---|---|---|
| 新增 Hub 后端（openclaw / 自定义） | ✅ 好 | `HubBackend` 接口 + 每 Agent 独立 backend，扩展点清晰 |
| 新增触发源（MCP / REST / CLI / Cron） | ⚠️ 中 | 需 `Intent.Source` 字段（1.3.2 已规划）；但 1.3 的迁移时机建议调整（P3-3） |
| 新增 role | ⚠️ 中 | 需先做 8.1 的描述表收敛，否则改 5 处 |
| 策略配置化（Phase 3） | ✅ 好（若采纳解析表） | 解析表 + gate 拆分（1.5.1 已规划）是天然基础 |
| 多平台（GitHub/GitLab） | ⛔ 明确不做 | 已在"明确不做"列出，`internal/ingress/gitea` 的命名为将来留了余地，合理 |
| Hub 长任务 / 断点续跑 | ❌ 差 | P2-1，同步 `Execute` 是硬伤，**Phase 1 定型前必须改** |
