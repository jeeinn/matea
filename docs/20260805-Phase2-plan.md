## 0. 背景与范围

Phase 1 把 Matea 定型为「可插拔 backend 的 Gitea AI Agent 网关」：`builtin`（进程内 Agent Loop）与 `hub-opencode`（OpenCode sidecar）已落地，stage 语义化、`gitea.auto_provision` 开关、文档闭环完成。

Phase 2 的目标：把 backend 生态从「雏形」扩展为**完整 Hub 生态 + 渠道接入**，让 Matea 既能把任务外包给外部 Hub（Hermes / 全 role OpenCode），也能作为 **MCP Server** 被 Hub 反向调用，并通过 **deliver** 模块把事件回传到 IM/Hub 渠道。更深一层：把「执行内核」抽象为**可插拔的 `Harness`**（D10），实现**模型无关**——builtin / OpenCode / Hermes / 乃至 Phase 3 的 Pi·Codex·Claude 都能作为执行内核替换（D11 ToolBox 统一集成面 + D12 统一 out-of-process 集成模型，不引入任何外部 harness SDK）。

**明确排除（不在 Matea 代码内实现）：**
- 不自研飞书/企微/钉钉 SDK（任务 2.3.5 明文）。渠道对接交由 Hub 或用户自配 bridge。
- 因此 2.4.x 的「飞书」用例，Phase 2 只交付 **Matea 侧契约（MCP Server + deliver）**，并以 **mock Hub** 做验收，不写真实飞书连通代码。

## 2. 决策点

### D1 ｜ Hermes 的本质定位（最关键，牵动 2.1 与 2.4）
**背景**：`hermes` 在任务里出现两次——既是要实现的 backend（`internal/agents/backends/hermes`，2.1），又是「飞书用户对话的对象」（2.4）。它到底是什么？

**选项**
- **A（推荐）Hermes = 外部 Hub/Ochestrator**。Matea 侧只实现两件事：
  - 出站：`hub-hermes` 类型的 `HubBackend` 适配器，把 repo 驱动的任务（Issue 被 Assign 给某 `hub-hermes` agent）Submit 给 Hermes HTTP API；
  - 入站：Matea 作为 **MCP Server**（2.3.1），让 Hermes 能通过 `matea_*` 工具反向查询/触发（2.4.1/2.4.2）。
  - 即 2.1 与 2.4 共享同一 Hermes 集成，Hermes 自身是独立服务。
- B Hermes = Matea 内建的编排层（替换 builtin 的 LLM 调用）。则 2.4 飞书对话仍需另接，割裂。
- C Hermes 仅作 backend，不做 MCP/渠道。则 2.4 无法成立。

**✅ 推荐 A**。理由：与 Phase 1 已建立的 `HubBackend` 抽象、`hub-hermes` 预留类型、2.3.5「不自研 SDK」完全一致；避免把对话/编排塞回 Matea。

**影响**：明确 2.1.1 的 `backends/hermes` 是「Matea→Hermes 的客户端适配器」而非 Hermes 本体；HTTP 集成对接官方 **Runs API**（`POST /v1/runs` + `GET /v1/runs/{run_id}` Poll + SSE），非 `/v1/tasks`；2.4 的飞书用例走「用户↔Hub(Hermes)↔Matea」链路，人类渠道由 Hermes gateway `deliver`（feishu 原生）承担。

**待拍板**：Hermes 是否为外部服务？Matea 是否仅做客户端适配器 + MCP Server？

### D2 ｜ Hub 任务完成通知模型（已据官方 API 核实：Poll 模型，无推送）
**背景（2026-08-05 核实）**：官方 Hermes API 是 **Runs API**——`POST /v1/runs` 提交、`GET /v1/runs/{run_id}` 轮询（SSE 可选进度），**无 `callback_url` 推送端点**（社区封装 `cnb.cool/seeio/hermes-hub` 的 `/api/v1/tasks`+`callback_url` 非官方，不作为集成目标）。OpenCode 当前为同步跑完、`Poll` 取终态。两者**都不会向 Matea 推完成事件**。

**结论（已拍板，并据事实修正决策 #4）**
- **完成通知 = Poll（复用 Phase 1.2.1 落库 + Executor 重启拾取 + 重启重放）**。
- **取消「独立入站完成端点」**——原决策 #4「入站完成端点并入 Hermes 适配器」前提（Hub 推送）不成立；Hermes 走 Poll 即可，无需 Matea 开 HTTP 入站接收完成事件。
- `Handle` 持久化（RemoteID + IdempotencyKey）仍按 1.2.1 强制点执行，支持重启恢复。

**影响**：D5 的 deliver 模块**只需出站扇出**（见 D5）；`HubBackend.Poll` 是唯一完成来源，OpenCode/Hermes 共用同一 Poll 实现。

**状态**：`[x]` 已拍板——采用 Poll 模型，无入站完成端点（原 push 方案废弃）。

### D3 ｜ 跨任务记忆共享机制（2.1.6）
**背景**：2.1.6 要求「同一 repo 上 analyze→review→code 记忆共享」。当前已有三条现成通道，但无结构化语义记忆。

**选项**
- **A（推荐）以 Gitea 评论为权威共享媒介 + `MemoryKeys` 结构化补充**。
  - analyze 的结论本就写成 Issue 评论；review/code 任务经既有 `comment_history` 注入已能看到（**现状部分已满足**）。
  - 新增：`TaskContext.MemoryKeys`（已预留）落地——analyze 结束时把「决策摘要」以 `repo+issue` 为键写入新增轻量 `memories` 行；review/code 任务读取并注入 prompt。不引入重型向量库。
- B 新建完整 memory 子系统（向量/图谱）。过度设计，Phase 2 不必要。
- C 仅靠 `AgentSession` 工作区复用。无法传递语义结论，analyze 的「为什么这么改」会丢失。

**✅ 推荐 A**。理由：复用已验证的评论注入通路，`MemoryKeys` 钩子已就位，成本低；明确 Gitea 评论即「人类与 Agent 共享的记忆」。

**影响**：Phase 2 仅需新增一个 `memories` 表（repo/issue 级 KV）+ `MemoryKeys` 读写；2.1.6 验收 ≡ analyze 写键、code 读键后行为一致。

**待拍板**：记忆共享是否采用「Gitea 评论为主 + MemoryKeys 结构化补充」？是否接受 2.1.6 现状已部分满足（评论注入）？

### D4 ｜ MCP Server 暴露范围与鉴权（2.3.1 / 2.3.2）— 降级为可选增强
**背景（2026-08-05 复核）**：Matea↔Hermes 主链路是 **HTTP Runs API**（`/v1/runs`），人类渠道由 Hermes gateway 的 `deliver`（feishu/wecom/… 原生支持）承担。因此「Matea 起 MCP Server 让 Hermes 反向查上下文」**不是 2.4 飞书验收的必需**——验证 2.4 用「Hermes runs API + Hermes 原生 deliver 到飞书 + Poll 回 Matea 写 Gitea」即可跑通。

**结论（已拍板）**
- **MCP Server（2.3.1）降级为可选增强**：若做，则严格按最小 4 工具（`matea_get_issue_status` / `matea_assign_agent` / `matea_list_agents` / `matea_post_comment`），API Key 鉴权、HTTP+SSE 传输，mTLS 延后。
- 不做 `create_issue`（Hermes 自管）、`list_open_issues`（Hermes 可直连 Gitea）、`reset_session`（高危，不对外暴露）。

- ⚠️ **实现前提更正（2026-08-06）**：`internal/agent/tools_mcp.go` 现有的是 **MCP Client**（Matea 消费外部 MCP 服务），与此处需要的 **MCP Server**（Matea 暴露工具）**方向相反、无法复用**，属全新实现。工作量评估须按「从零起」计。

**影响**：Phase 2 最小可用交付**不含** MCP Server；2.4 验收不依赖它。系统配置页仍保留 MCP 配置块（2.3.5）以便后续启用。若后续落地，其暴露的工具集须遵循 D11 分层策略（Gitea 读侧 + 网关级 skill script，沙箱类默认不给）。

**状态**：`[x]` 已拍板——MCP Server 降级可选，工具数 = 4（若实现）；确认为全新实现，非复用现有 MCP Client。

### D5 ｜ deliver 模块定位与 `deliver.webhook_url` 语义（2.3.3 / 2.3.4）— 仅出站扇出
**背景（2026-08-05 复核）**：原计划称 deliver「双向」（出站 + 入站完成回传）。据官方 API 核实：Hermes 无完成推送端点（Poll 模型）、OpenCode 同步跑完，**均不向 Matea 推完成事件** → 入站完成端点无存在必要。评审报告风险 2（deliver 双向 = 两子系统塞一名）据此收敛为**仅出站**。

**结论（已拍板）**
- **deliver = 出站事件扇出，叠加在 Gitea 写回之上（不替代）**。Matea 仍是 Gitea 唯一写方；deliver 把「任务完成/状态变更」事件 POST 到 `deliver.webhook_url`（用户自建 IM bridge 或 Hub 接收端）。
- `webhook_url` **全局单一**，事件自带 `Channel` 字段供路由；失败可丢（Gitea 评论已是权威记录）。
- **无入站接收模块**（呼应 D2）：Hermes 完成经 Poll 取回、OpenCode 同步返回，不走 deliver 入站。
- 2.2.x（OpenCode 无 IM）与 2.4.x（Hermes 自带渠道时可选不配）共用同一出站 deliver 路径。

**影响**：deliver 模块**仅需出站实现**；新增 `deliver.webhook_url` 配置；2.2/2.4 直接复用。

**状态**：`[x]` 已拍板——deliver 仅出站扇出，全局单一 `webhook_url`，无入站端点。

### D7 ｜ hub-opencode 扩展为全 role（2.2.1 / 2.2.2）— 已拍板，附「工作区上下文增强」
**结论（已拍板）**：
- `hub-opencode` 仍需扩为全 role backend（analyze/review/reply/write 均可走 OpenCode）。
- 其中 **「analyze 带工作区给 OpenCode」作为 D7 第一刀（最小可验证）**；随后 review（可选带工作区）、reply（对话类）一并排进 D7 实施计划。
- D1–D6 / D8 / D9 其余决策按文档建议实施。

**背景**：当前 `hub-opencode` 仅支持写入类（dev/bugfix），靠 `opencodeWriteSubType` 拒绝非写任务（`opencode_http.go:566`）。2.2 要扩到 analyze/review/reply。

**关键技术依据（已逐文件核验，2026-08-05）**：
1. **analyze 路径本就带工作区（builtin 下已落地）**：`AnalyzeRunner.Run`（`runner_analyze.go:40-62`）已调用 `prepareAnalyzeWorkspace` 对默认分支做 shallow clone，再跑最多 5 轮只读 AgentLoop。即「issue 分析带工作区」在 builtin 下已实现。
2. **`prepareAnalyzeWorkspace` 已存在**（`write_workspace.go:322-378`）：默认分支 shallow clone、只读、**不建分支/不推送**、`UseSession:false`（临时 sandbox），由调用方 `defer wwc.Sandbox.Cleanup()` 销毁。
3. **OpenCode session 本就按目录绑定工作区**：`createSession`/`sendMessage` 传 `?directory=` + `X-Opencode-Directory`（`opencode_http.go:185-211,254-308`）；`Submit` 已吃 `tc.SandboxPath`（`opencode_http.go:497`）。把工作区传给 OpenCode = 零新增协议代码。
4. **隔离零成本**：analyze 用临时 sandbox，`defer Cleanup()` 已兜底——即使 OpenCode 在分析时改了文件，也随临时目录销毁，不污染共享工作区或后续 code 任务。
5. **质量收益**：builtin 分析把代码截断注入 prompt（受 maxInput 限制）；OpenCode 拿到完整仓库 FS 读权限（目录绑定，自行 Read/Search），上下文比 builtin 截断**更完整**，Matea 侧还省了代码截断注入逻辑。

**✅ 推荐方案（分三刀，第一刀最小可验证）**

- **第一刀（最小可验证 · 2.2.1）`AnalyzeRunner` 后端感知 + analyze 带工作区给 OpenCode**
  - `AnalyzeRunner.Run`：`if agent.Backend==hub-opencode` 分支 → 复用 `prepareAnalyzeWorkspace` 拿 `WorkDir` → 调 `OpenCodeHTTPBackend.Run(WorkDir=...)` → 取 summary 写成评论（**不建 PR**）→ `defer wwc.Sandbox.Cleanup()`。
  - 放宽 `opencodeWriteSubType` → 改写为 `opencodeSubType(taskType) → (subType, isWrite)`：analyze/review/reply 返回单轮标记，write 类返回 dev/bugfix。

### D10 ｜ 大脑可插拔：统一 Harness 抽象（Phase 2 地基）

**✅ 推荐方案（升格为 Phase 2 地基，先于 2.1/2.2）**
- 收敛为**一个 `Harness` 接口**：`Profile() HarnessProfile` + `RunTurn(ctx, HarnessTurnInput) (*HarnessTurnResult, error)` + `Close()` + `ResetSession(id)`。
  - `HarnessTurnInput`：`Task TaskContext`（issue/PR 内容、role、history）+ `Tools ToolContext`（Matea 拥有的工具）+ `Model string`。
  - `HarnessTurnResult`：`Reply string` + `Action string`（`comment`/`create_pr`/`none`）+ `PendingApprovals []Approval`。
- **`builtin` 成为其中一个 in-process adapter**（内部仍跑现有多 role Agent Loop）；`hub-opencode`/`hub-hermes` 改造为 **out-of-process adapter**（见 D12）。

- **拒绝 qm 的两点**：① 每轮动态选 harness（Matea 任务有状态 session/工作区/Handle，一个 Issue 不会中途换内核，选择粒度 = 每任务/每 agent）；② harness×model 双轴校验矩阵（Matea 的 model 仅 builtin 用、hub-* 自管 LLM，二者非正交轴）。

**状态**：`[x]` 已拍板——统一 `Harness` 抽象升格为 Phase 2 地基；builtin 作为 in-process adapter；拒绝每轮动态选 harness 与双轴矩阵；Pi/Codex/Claude 列为 Phase 3 候选（见 D12）。

### D11 ｜ ToolBox 接口（harness 与 Matea 的集成面 · 分层暴露）

**背景**：qm 让「任意 harness 可插拔」成立的真正设计动作是——**工具由 core 拥有，harness 只调用**（qm 的 `HarnessTurnInput.tools: ToolContext`）。harness 不实现任何业务工具（不碰 Gitea/沙箱内部），只拿 core 给的 `ToolContext` 做 tool-calling。这天然契合 Matea「Gitea 唯一写方、hub 不直连」的不变量。

**⚠️ 与 qm 的结构性差异（必须写进设计，否则实现时必撞）**：qm 的 harness 是它**自研的适配层**，工具集完全可控，因此能做到「core 的工具即 harness 的全部工具」。而 OpenCode / Hermes 是**成品 agent，自带工具且关不掉**。所以 Matea 的 ToolBox 对远程 harness 只能是 **append（追加）**，**不可能是 replace（替换）**。给远程 harness 再塞一套 `read_file`/`write_file` 是负收益——重名冲突、语义不一致、模型在两套同功能工具间摇摆，还比它直读本地盘多一个 round-trip。

**代码现状核对（2026-08-06）**
- `internal/agent/tools.go`：现有 **10 个工具全为沙箱工具**，全部绑定 `*sandbox.Sandbox` —— `read_file`/`write_file`/`list_files`/`search_code`/`rg`/`run_command`/`apply_diff`/`tree`/`git_log`/`git_blame`。
- **当前没有任何 Gitea 工具**：发评论、建 PR、读 issue 全在 runner/executor 层由 Matea 在 harness 返回结果后统一落地，从不作为工具暴露给模型（这正是「结果驱动」模型）。
- `internal/agent/tools_skills.go`：已实现 skill 渐进披露（扫 **gatewayDir** 与 **workspace** 两个根下的 `skills/`、`.agents/skills/`；`list_skills`/`load_skill`；skill 的 tool 为 shell script 经 `sb.ExecuteShell` 执行；analyze 模式 `allowScripts=false` 只注入指令正文）。
- ⚠️ `internal/agent/tools_mcp.go` 现有的是 **MCP Client**（Matea 消费外部 MCP 服务）。D11/D4 需要的是 **MCP Server**（Matea 暴露工具给远程 harness）——**方向相反，属全新实现，不能复用**。原表述「设计预留可 MCP 导出」易被误读为已有基础设施可借力，此处更正。

**✅ 推荐方案（三层暴露策略，非拍平的大集合）**

| 类别 | builtin | 远程 harness | 理由 |
|---|---|---|---|
| **沙箱类**（现有 10 个） | 必需，直连 Go 函数 | **默认不暴露** ✅拍板 | 成品 harness 自带同名工具，且直接操作共享目录更快；避免打架 |
| **Gitea 类**（新增） | 需要 | **必须经此**，唯一通道 | 「Gitea 唯一写方」的真正落点 |
| **Skill 类**（已有） | 已有 | 仅**网关级** skill 需暴露 | 见下「Skill 处置」 |

**三条拍板约束**
1. **Gitea 类 Phase 2 只做读侧** ✅：`gitea_read_issue`、`gitea_read_pr_diff`。**写侧（`gitea_create_comment`/`gitea_create_pr`）不做**，继续由 Matea 在结果返回后统一落地。理由：给 harness 写侧工具即等于「推理中途可写」，会引入乱序评论、重复评论、部分失败等不可回滚风险；写侧工具留 **Phase 3** 再评估。
2. **沙箱类对远程 harness 默认不暴露** ✅：远程 harness 自带文件工具且直接操作共享工作区（D7 的 `?directory=` 绑定），经 ToolBox 转一道是纯损耗。仅当 `workspace_transport = mcp`（L2 隔离档，Phase 3）时才按需暴露。
3. **配置提前留 `workspace_transport` 语义位** ✅：Phase 2 **只实现 `shared_path`**，Phase 3 补 `mcp` 时零返工（见下「部署档位」）。

**Skill 处置（分开处理，不做统一抽象）**
- **仓库内 skill**（workspace 的 `skills/`）——**不需要专门集成**。工作区一旦交付给 harness（D7 第一刀），harness 自己就能读到这些文件（OpenCode 还会自读 `AGENTS.md`）。经 ToolBox 转一道属多余。
- **网关级 skill**（gatewayDir 的 `skills/`）——**Matea 的运营资产，必须经 ToolBox**，因为远程 harness 的文件系统里没有这些文件。做法分两半：skill **正文（body）** 作为 system prompt 片段注入（任何 harness 都吃得下，零成本）；skill **script 工具** 经 ToolBox/MCP 导出，在 **Matea 侧沙箱内执行**。
- **远程 harness 自身的 skill/plugin 机制**——**不接管**。OpenCode 有 plugin、Claude Code 有 skills，各管各的。Matea 只保证「自己的 skill 能被任何 harness 用到」，不做统一抽象。此边界不划清，D11 会无限膨胀。
- ⚠️ **安全约束（Phase 3 落 MCP 时强制）**：skill 的 script 是任意 shell，一旦经 MCP 暴露给远程 harness 即等于开放**远程命令执行入口**。必须同时满足：① 只在沙箱工作目录内执行；② API Key 鉴权；③ 单 workflow 作用域绑定。三者缺一不可。

**部署档位（同机 / 异地由「工作区如何抵达 harness」决定，与 ToolBox 正交）**

| 档位 | 工作区传输 | 部署形态 | 适用 |
|---|---|---|---|
| **L0 同进程宿主** | 本地绝对路径 | Matea 与 harness 同机同盘 | 现状 `hub-opencode` |
| **L1 共享卷** | 共享挂载路径 | 同集群/同宿主，卷共享 | 容器化部署 |
| **L2 全隔离** | 经 MCP 文件工具 | 真异地，跨组织边界 | Phase 3；Hermes 天然属此档 |

- **现状已锁死 L0/L1**：`opencode_http.go` 用 `filepath.Abs(req.WorkDir)` 把**绝对本地路径**塞进 `?directory=` 与 `X-Opencode-Directory` —— 即 `hub-opencode` 事实上**要求同机或共享卷**，配个 URL 并不能异地。此点须在文档与配置校验中**显式声明**。
- **Hermes Runs API 纯文本 in/out，无工作区概念**，天生 L2；反面是**它看不到代码**（除非经 MCP 给文件工具）。这解释了为何 Hermes 适配天然只适合 analyze/reply 这类不需深挖仓库的 role。
- **L2 的代价**：agent loop 内每次 `read_file` 都是一次 MCP round-trip，大仓库上会比 L0 慢一个数量级。**L2 是为「组织边界隔离」付的性能税，不是升级。**
- **L1 并发约束**：共享卷下 Matea 与 harness 并发写同一目录，须明确「单 workflow 期间独占该工作区」。

**影响**：`ToolBox` 是 builtin 与远程 harness 的集成面，但按类别**分层暴露**而非统一大集合；远程 harness 只接 Gitea 读侧 + 网关级 skill。D12 的 out-of-process 集成模型依赖它落地。MCP Server 为**全新实现**（与现有 MCP Client 方向相反），Phase 3 落地。

**状态**：`[x]` 已拍板（2026-08-06）——① Gitea 工具 Phase 2 **只做读侧**，写侧留 Phase 3；② 沙箱类对远程 harness **默认不暴露**；③ 配置留 `workspace_transport` 语义位，Phase 2 只实现 `shared_path`；④ 对成品 harness 只能 append 不能 replace；⑤ 网关级 skill 经 ToolBox、仓库内 skill 随工作区、远程 harness 自身 skill 机制不接管。

### D12 ｜ 统一 out-of-process 集成模型（不引入外部 harness SDK）

**背景（2026-08-06 研判）**：你追问「OpenCode 乃至 Hermes、Codex、Claude Code 是否也支持 SDK 接入，是否影响大脑可插拔的集成方式」。核实各 harness 真实接入形态：

| Harness | 进程内 SDK 嵌入 | 远程/子进程接入 | 对 Go 的 Matea |
|---|---|---|---|
| OpenCode | ✅ `@opencode-ai/sdk-next`(TS) + plugin | ✅ `opencode serve`(HTTP+SSE,`?directory=` 绑目录) / ACP(stdio) / `run`(CLI) | TS 嵌入无用 → 走远程 HTTP |
| Hermes | ⚠️ Python `import run_agent.AIAgent`（社区不建议生产嵌入） | ✅ API server(HTTP+SSE `/v1/runs`) / TUI gateway(stdio/WS) / ACP | 远程优先；Python 嵌入无用 |
| Claude Code | ✅ `@anthropic-ai/claude-agent-sdk`(TS) | ✅ CLI 子进程 / headless | TS 无用 |
| Codex | ✅ `@openai/codex`(TS) | ✅ app-server JSON-RPC / CLI | TS 无用 |
| Pi | ✅ `@earendil-works/pi-coding-agent`(TS) | （主要 in-process） | TS 无用 |
| builtin(Matea 自有) | ✅ **真·Go 进程内** | — | 唯一能真·进程内 |

**结论（已拍板）**
- **所有外部 harness 都是 TS/Python/独立二进制，无一个能真嵌进 Go 进程**。「SDK 接入」对 Matea 全是浮云——我们不 `import` 任何外部 harness SDK，而是把它们当**外部进程/服务**去 spawn 或连接。
- **统一集成模型（2×2 子集）**：

  ```
                  toolTransport
                ┌──────────────┬──────────────────┐
  controlTransport │ submit-contract │   mcp(Phase 3)   │
  ┌─────────────┼──────────────┼──────────────────┤
  │ in-process  │ builtin(Go)  │ （不需要）        │
  │ out-of-proc │ hub-opencode │ hub-* 实时工具    │
  │ (HTTP/stdio)│ hub-hermes   │ 调用(Claude/Codex)│
  └─────────────┴──────────────┴──────────────────┘
  ```

  - **`submit-contract`**（Matea 传上下文、收回结果/动作、自己执行工具）= 现状 `hub-opencode` 模式，也覆盖 Hermes `/v1/runs`。**无需 MCP，天然守唯一写方**。
  - **`mcp`**（harness 在 loop 实时回调 Matea MCP server 拿 Gitea/沙箱工具）= Phase 3 才有需要（如 Claude Code 边读文件边审查）。
- **Pi/Codex/Claude 明确列为 Phase 3 候选**：接入方式 = spawn 其 CLI / 连其本地 server（out-of-process），**不引入其 SDK**。机制验证后 trivial 接入。
- Harness 接口仍**声明** `controlTransport`/`toolTransport` 元数据（对齐 qm、利于文档），但 concrete adapter 只需实现「in-process(builtin) + out-of-process(submit-contract 为主)」。

**影响**：彻底消解「外部 LLM SDK 进 Matea」边界风险；D7（analyze+workspace）与 hub-hermes `/v1/runs` 都是 out-of-process HTTP，Transport 一致，既有 `opencode_http.go` `?directory=` 目录绑定即现成实现，无需返工。

**状态**：`[x]` 已拍板——统一 out-of-process 集成模型；builtin 唯一真·进程内；其余 spawn CLI / connect HTTP 或 stdio-RPC；不引入任何外部 harness SDK；Pi/Codex/Claude 列 Phase 3。
