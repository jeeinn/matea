## 总体评价

骨架设计健康：键白名单（`IsConfigKey`）+ 参数化 SQL 杜绝注入、`auth.jwt_secret` 不在可导入键集内；env-detection 值从不出进程、审计只记变量名不记值；掩码恢复链双层且 fail-closed；31 个注册键导出全覆盖；sysinfo 三文件 build tag 互斥全覆盖、Windows 用 quota 感知 API；LLM 探测走 `/models` 零费用；前后端五端点契约逐字对齐；无 XSS 面。

但存在贯穿性裂缝：**宣称的安全语义与实现不符**（导出号称脱敏实则全明文且无审计、运行日志明文记录密钥架空审计掩码），以及两个击穿主用例的功能性 bug（健康面板读启动快照、向导 env 吸入脱节）。

## 🔴 必修 Bug（8 项）

### R1 健康面板读启动快照，热更新后永久失真（最严重）
`internal/api/health.go:112,152,216,281,317` 全部读 `h.cfg`（`NewHandler` 传入后永不更新），而 `ConfigManager.Update` 热更新只替换 manager 内部快照（`internal/config/manager.go:116-122`）。
**后果**：首次启动 → 向导完成配置后，Dashboard 健康面板仍显示「未配置」，直到重启。C-18/C-19 主用例被击穿。
**修复**：各 `check*` 改用 `h.cfgManager.Get()`（一行级改动）。

### R2 `HumanBytes` 单位错位一档 + 小字节恒为 "0 B"
`internal/sysinfo/disk.go:62-71`：`b<1024` 返回 `"0 B"`；`div` 从 1024¹ 起步而 `units[exp]` 从 "B" 起步——5 GiB 打印成 "5 MiB"。main.go 启动告警与磁盘组件数值全部错误。另 `trimFloat`/`itoa` 手写重复造 `strconv` 轮子。

### R3 deliver Webhook URL 的 query token 泄漏
`internal/api/health.go:360-369` `maskURL` 只掩 userinfo 不掩 query（注释谎称掩了）——钉钉/飞书 webhook 的 `?access_token=` 明文进入健康响应；端点仅 `jwtWrap` 无角色限制（`internal/api/router.go:86`），普通登录用户在 Dashboard 可见。

### R4 SetupWizard env 吸入与向导脱节，webhook_secret 被静默替换
`web/src/views/SetupWizard.vue:324-340` 吸入成功后不回填表单、不解锁步骤（step1 按钮被 `:disabled="!gitea.url || !gitea.token"` 锁死）；`internal/api/setup.go:211-247` `completeSetup` 无条件用表单值覆盖，且请求不带 secret 时**总是生成随机 secret 覆盖**——env 吸入的 `GITEA_WEBHOOK_SECRET` 在 finish 时被静默替换、旧值不可恢复。另 apply-env 从不设 `llm.defaults.model`，「吸入即完成初始化」路径不存在。

### R5 C-20 导出明文密钥 — 与原始规格矛盾 + 无审计
`internal/api/config_io.go:15-19` 自承 "Secrets are included"：`gitea.admin_token`、`webhook_secret`、全部 LLM api_key、hub backend password 明文下发。原 P2 规格为「**不含 secrets**（敏感字段脱敏）」，docs commit `230eecc` 将规格改写为「含真实密钥」追认实现。该端点是全系统唯一能批量导出全部密钥的入口，却**无审计日志**（import / apply-env 都有 `LogOperation`）；测试还将明文导出固化为断言（`internal/api/health_env_test.go:262-264`）。
**修复建议**：默认脱敏 + `?include_secrets=1` 显式开关 + 导出审计。

### R6 `ConfigManager.Update` 把密钥明文写进运行日志
`internal/config/manager.go:130` `log.Printf("Config updated: %s = %s", key, value)`（启动加载路径 L79/83 同样）。存量问题，但 C-20 导入 / C-21 吸入把全套密钥成批推过此路——审计层掩码被运行日志整体架空。

### R7 导入/吸入非事务 + map 随机顺序 → 部分失败持久化、结果不稳定
`config_io.go:129-136` 逐键 `Update` 立即落库；map 迭代顺序随机，而 `agents.loop.*` 的 `ValidateAgentLoopConfig`（`internal/config/keys.go:297-304`）对中间态组合校验——同一导入文件多次执行可能偶发不同失败。前端还丢弃响应 `errors`（`SystemConfig.vue:1723`），部分失败仍提示「配置已导入」。
**修复建议**：ConfigManager 增加批量/事务 Update（一并解决 providers/backends 的 read-modify-write 竞态）。

### R8 前端交互硬伤
- **导入零确认零预览**：`SystemConfig.vue:521-527` 文件 `on-change` 即 POST 覆盖全部配置，无 ElMessageBox 确认、无 diff 预览、无大小限制（后端亦无 `http.MaxBytesReader`）。
- **Dashboard 与内嵌 HealthStatus 重复请求** `/health/summary`（`Dashboard.vue:208-214` + `HealthStatus.vue:60`），后端探测**全串行**（`health.go:72-87`），3 个 hub 全挂时单请求 ~27s+，超过 `main.go:271` 的 15s WriteTimeout；外层 ctx 形同虚设（`withTimeout` 不听 ctx、`checkGitea` 不用 ctx）。
