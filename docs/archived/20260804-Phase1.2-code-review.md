### 🟡 非阻塞一致性说明（不要求返工，建议记录）
1. **摘要「五 Runner」为误数**：实际只有 4 个 runner 文件（analyze/interaction/review/write），且 `validateHubDispatch` 已接入全部 4 个，覆盖**无缺口**。规划文档此前亦称「四个 Runner」，建议把摘要文字改为「四 Runner」以免后人困惑。
2. **两个 HubBackend 实现在 Phase 1 均为同步执行 + 内存结果缓存**：这是既定范围（真异步 Submit/Poll 留 Phase 2）。需注意——`BuiltinHubBackend` 适配器当前**未被生产 runner 调用**（runner_write.go 仍走 CodingBackend 路径，validateHubDispatch 只校验不切换），属于「证明接缝、尚未接管生产路径」的 seam-proof 实现。这与你自己的备注「生产 Runner 执行路径未切换（Submit/Poll 真分流留待 Phase 2）」一致，特此确认无遗漏。
3. **`Handle.IdempotencyKey` 已计算但 Phase 1 未用于去重**：两个实现都以 `RemoteID` 为缓存键，未消费 `IdempotencyKey`。字段用途（防重复提交）的强制逻辑属于 Phase 2（持久化 Handle + Executor 重拾）范畴，当前为「字段就位、逻辑待接」，与整体节奏一致，但建议在 TASKS Phase 2 明确挂一笔「IdempotencyKey 去重落地」。
4. **接口注释「Poll 须重启后仍安全」对同步后端略乐观**：`hub_backend.go:172-174` 称 Poll 重启后安全（given persisted Handle），但 builtin/opencode 的 Handle **未持久化**，重启后 Poll 返回「unknown handle」错误。实现文件注释（builtin_hub_backend.go:104-107、opencode_http.go:531-533）已澄清「同步后端不存在跨重启 Handle」，故不构成 bug，仅接口总注释与实现局部注释存在轻微张力，可在 Phase 2 接管持久化时统一措辞。
