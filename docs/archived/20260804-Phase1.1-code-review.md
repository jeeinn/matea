## 三、代码审查发现

### 🔴 P1（建议在标记 1.1.4a 完成前处理）：解析表 `TaskTypeTable` 是孤儿代码，未接入 resolver

`internal/workflow/tasktype_table.go` 定义了 `TaskTypeTable` 与 `ResolveTaskType`（带 242 行测试），但**全仓生产代码零调用**：

- `resolver.go:146` `resolveAssigned` 仍走旧 `taskTypeForRole`（定义于 `:220`）
- `resolver.go:347` `resolveComment` 仍走旧 `commentTaskType`（定义于 `:378`）
- `resolver.go:191` `resolveReviewRequested` 硬编码 `"review_pr"`

`grep ResolveTaskType` 仅在 `tasktype_table.go`（定义）与 `tasktype_table_test.go`（测试）出现。

**后果（严重）**：
1. **我此前专门要求的回归防护并未生效。** 表里有 `{RoleReview, Issue, Mention}→reply_comment` 和 `{RoleReview, PR, Mention}→reply_comment`（标注 `// Critical: NOT review_pr`），但 resolver 的 `commentTaskType` 对 review role 同样返回 `reply_comment`——这条恰好一致，所以 mention 路径没回归。**真正的隐患在 Assign 路径**：`taskTypeForRole(RoleReview)` 无条件返回 `"review_pr"`（`:235`，不区分 surface）。若把 review agent assign 到一个 **Issue**（非 PR），旧逻辑产出 `review_pr`，会被 L1 门禁 `checkReviewRequiresPR` 拒绝 → 静默不响应。表里没有 `review+issue+assign` 项（正确返回空），但表没被用，所以线上仍是旧的危险行为。
2. **三套 task_type 逻辑并存**：表 / `taskTypeForRole` / `commentTaskType`。维护者若在表里「修复」映射，运行时毫无变化——典型的陷阱。
3. **1.1.4a 任务描述「抽取三元组解析表」的承诺未兑现**：表抽出来了，但消费层没改造，Phase 3 策略配置化所依赖的「单一映射真相」并未建立。

**建议（二选一，强烈建议前者）**：
- **(A) 接表**：在 `resolver.go` 增加 `intent` 推导（assign / review_requested / mention / slash_dev / slash_reply），用 `DetermineSurface` + `ResolveTaskType(role, surface, intent, evt)` 替换 `taskTypeForRole` 与 `commentTaskType`；`ResolveTaskType` 返回空时 `Resolve` 返回 nil（不触发）。
  - 行为一致性已核对：mention / slash 路径表与旧逻辑完全一致；唯一差异是 review+issue+assign 从「产出 review_pr 后被门禁拒」变为「不触发」——属改进，但应作为显式验收点写进测试。
- **(B) 若接表需更大的子任务、本阶段不做**：必须在该表与测试顶部加醒目标注「当前未接入 resolver，仅作为规格参考 / 后续 1.1.4 收尾使用」，避免他人误改无效代码。
