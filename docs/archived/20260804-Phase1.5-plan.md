# Phase 1.5 实施方案：工作流与体验

> 日期：2026-08-04 ｜ 目标：在 Phase 1.4 收官后，收尾「工作流与体验」三项的真实剩余工作
> 范围：不改动业务行为的大前提下，修复 stage 滞留缺陷、收敛 stage 的用户可见面、补齐 auto_provision 开关

## 一、现状核对（基于代码，非凭文档）

### 1.5.1 保留 free/standard/strict 预设 + gate 评估拆独立函数
- `internal/workflow/policy.go` 中 gate 评估**已是独立函数**：`evalRerunSameStage` / `evalCoderRequiresAnalyzed` / `evalReanalyzeWhileDev` / `evalCoderSwitchAgent` / `evalReviewNotSameCoder`，统一经 `EvaluateGate(policy, gateID, ...)` 分发（`policy.go:175`）。
- 三套预设 `free/standard/strict` 对应 `off/soft/hard`，已定义在 `policy.go:54-103`。
- **结论：此项大概率已实现**，主要是核验 + 在 TASKS 勾选，而非新写代码。若核验发现仍有内联 gate 逻辑未抽离，则补抽离。

### 1.5.2 隐藏 stage 用户可见面 + 修复 stage 滞留
- **缺陷根因已定位**：
  - 入口：`internal/dispatcher/pipeline.go:111` 对**每一个** resolved 事件都调用 `d.wfMgr.Transition(ctx, result.Role)`，把 stage 推到 `analyzing`/`developing`/`reviewing`。
  - 回落缺失：`internal/workflow/context.go` 的 `OnTaskComplete`（L103-126）对 `reply_comment`/`solve_comment` 只写 PR ID、**不回落 stage**（L117-121）。
  - 后果：@提及触发的回复类任务（如 `@matea-analyst` 在评论里被 @）跑完后，stage 永远卡在 `analyzing`（与 TASKS 描述完全吻合）。
- **stage 用户可见面**：`web/src/views/WorkflowDetail.vue`（路由 `/workflows`，**非 admin 限定**）直接展示 `stage` 列 + `stage-flow` 可视化 + `previous_stage`。这是内部实现细节泄漏给普通用户。grep `web/src` 中 `stage` 仅出现于 `WorkflowDetail.vue` 与 `SystemConfig.vue`（gates 配置），即 stage 仅此一处面向用户。

### 1.5.3 保留 EnsureGiteaAccount，默认开、可配置关
- `EnsureGiteaAccount` 定义于 `internal/agents/manager.go:100`，调用点 `manager.go:156`（createAgent）/ `manager.go:200`（updateAgent）。
- 当前**无** `auto_provision` 配置开关（grep `AutoProvision`/`auto_provision` 在 `internal/` 下零命中）。即目前永远自动建号。
- 1.1.3 已实现账号劫持防护（仅 Matea 托管账号可重置密码/签发 token）。1.5.3 在其外层加开关，不改动防护逻辑本身。

## 二、分项实施

### 1.5.1 核验 + 关闭（低风险）
- 读 `policy.go` 全量，确认 gate 评估函数拆分满足「独立、便于 Phase 3 配置化」；确认 `WorkflowPolicy` 预设结构可被 Phase 3 直接消费。
- 若发现仍有内联 gate 逻辑未抽离 → 补抽离；否则直接在 `docs/TASKS.md` 勾 `[x]`，附核验说明。
- **不动** preset 语义（free/standard/strict 维持 off/soft/hard）。

### 1.5.2A 后端修复 OnTaskComplete（中风险，核心）
- 文件：`internal/workflow/context.go`
- `reply_comment` 分支：完成时**回落** `stage` 到 `PreviousStage`，并清空 `ActiveAgentID`/`ActiveRole`/`SessionID`（与 `OnTaskFailed` 的 analyze 回滚一致，参考 L130-147）。
- `solve_comment` 分支（**需拍板**，见下「待拍板项」）：
  - 推荐规则：若已创建 PR（`prID>0`）则保持 `developing`（与 `solve_issue` 一致）；若未创建则回落 `PreviousStage`。
  - 备选（与任务字面最贴合）：一律回落 `PreviousStage`。
- 新增单测：
  - `TestOnTaskCompleteReplyCommentRollsBack`：`reply_comment` 从 `analyzing` → `PreviousStage`（或 `idle` 兜底）。
  - `solve_comment` 对应用例（PR 创建 vs 未创建两种）。
- 验收：@提及 analyst 触发 `reply_comment` 后，stage 不再滞留 `analyzing`。

### 1.5.2B 前端隐藏原始 stage（中风险）
- 文件：`web/src/views/WorkflowDetail.vue`
- 主展示改为**语义状态**：由 `stage` + 是否已有 PR/最近任务推导「Agent 正在处理 / 已回复 / 已创建 PR / 已完成」，作为列表/详情的主标签。
- 原始 `stage` 列与 `stage-flow` 可视化**不再作为默认用户可见面**：
  - 收进「诊断（高级）」折叠，或仅 admin 可见（**需拍板**，见下）。
  - `previous_stage` 同理隐藏。
- **后端契约不变**：`GET /api/workflow-context` 仍返回 `stage`（供诊断/admin 与集成测试），仅前端做语义映射，避免破坏其他消费者与集成测试。

### 1.5.3 EnsureGiteaAccount 可配置关闭（低风险）
- 配置：`config` schema 的 `gitea` 段加 `auto_provision bool`（yaml `auto_provision`，**默认 true**）；`config.full-example.yaml` 补注释。
- 代码：`manager.go` 两处 `EnsureGiteaAccount` 调用前置判断：`auto_provision==false` 时跳过自动建号，仅做名称建议/校验（沿用 1.1.3 既定语义「`gitea.auto_provision: false` 时只做名称建议，不触碰 Gitea」）。
- 测试：新增用例——`auto_provision=false` 时不调用 `AdminUpdateUserPassword` / 不签发 token（mock 验证）。
- 注意：1.1.3 账号劫持防护逻辑保留，仅在外层加开关。

## 三、实施顺序建议

1. **1.5.1 核验**（小，先关闭一项建立信心）
2. **1.5.2A 后端修复**（含单测，行为正确性优先）
3. **1.5.2B 前端语义化**（依赖 2 的 stage 语义稳定）
4. **1.5.3 配置开关**（独立，可与 2/3 并行）

2. **1.5.2B 隐藏粒度**：
   - (a) WorkflowDetail 全部改为语义状态，原始 stage 完全不展示；
   - (b) 保留原始 stage 但收进 admin/诊断折叠（推荐：保留诊断能力、默认只显语义）。
