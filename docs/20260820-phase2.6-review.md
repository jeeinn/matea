## 二、发现的偏差

### 2.1 ⚠️ C1：mcp transport 的运行时报错文案与 TASKS.md 承诺不符（轻微）

- **TASKS.md 声称**：config 报错文案更新为 `"removed in C1（Phase 3.9 回归）"`。
- **实际代码**：`internal/config/config.go:339-341` 对 `mcp` 输出的是通用拒绝文案 `workspace_transport %q is not supported (valid: git_sync)`；`"removed in C1"` 字样仅存在于代码注释（`config.go:330`、`schema.go:319/341`）、测试名与 `docs/HUB-BACKENDS.md:116`。
- **影响评估**：行为正确（fail loud、启动期即拒绝），仅文案不含迁移指引；用户看到通用报错也能从 `valid: git_sync` 推断解法。**属文档与代码的措辞偏差，非功能缺陷。**
- **建议（二选一）**：① 给 `mcp` 加专用迁移报错文案兑现承诺；② 将 TASKS.md C1 描述修正为通用拒绝文案。鉴于 Phase 3.9 才计划回归 mcp，建议采用成本更低的 ②。

### 2.2 ⚠️ 面向用户的文档漂移（超出 TASKS.md 勾选范围，但直接影响用户）

C2 文档收尾覆盖了 `HUB-BACKENDS.md` / `CHANGELOG.md` / `remote-hub-deployment-flow.md`，但**两份用户入口文档仍是 shared_path 时代的描述**，与 A5（删除 shared_path）、B1（Hermes 落地）之后的现实矛盾：

| 位置 | 过时内容 | 应改为 |
|------|----------|--------|
| `README.md:337` | 配置示例含 `workspace_mode: matea_path`（注释「Phase 1 仅支持 matea_path」） | `workspace_transport` 已收敛为仅 `git_sync` 且为默认值，该行应删除 |
| `README.md:354` | 「OpenCode 在 Matea 准备的沙箱路径工作，Matea 仍负责 git/PR」 | git_sync 契约下 OpenCode 持任务级 deploy key 自 push 草稿分支，Matea 四要素校验后开 PR |

**影响评估**：新用户按 README 配置会得到能跑通但语义陈旧的配置（`workspace_mode` 是废弃兼容字段），且对 Hermes 可用性产生误判。建议作为 Phase 2.6 收尾的补遗项处理。
